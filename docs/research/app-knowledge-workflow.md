# App 知识的学习与记录流程

*2026-10-19。*

| 文档 | 讲什么 |
|---|---|
| [operation-playbook-design.md](operation-playbook-design.md) | playbook 的格式 |
| 本文 | **知识从哪里来、怎么记、怎么验证和维护** |

> **开源和商业的边界**：
> - 本文和格式规范是开源的；
> - 具体某个 App 的知识（选择器、流程、deep link、弹窗、陷阱）是商业资产，存放在**私有库**，不进这个公开仓库。现在的私有库是本地目录 `LoopCtrl-Playbooks`，和 LoopCtrl 仓库并列，只有本地 git。

---

## 1. 原则

1. **知识是「带条件的观察」，不是结论。** 每条都要写清：
   - 在哪个 App 版本、哪一屏；
   - 看到了什么；
   - 建议怎么做；
   - 证据是什么。
2. **每条都有状态，状态决定运行时能不能用**：

   | 状态 | 含义 | 运行时 |
   |---|---|---|
   | `lead` | 线索 | 只作提示 |
   | `observed` | 我们见过 | 提示，并优先验证 |
   | `verified` | 按版本复现过 | 执行器可以直接用 |
   | `regression` | 每次 App 更新都会自动复测 | 执行器可以直接用 |

3. **来源要能追溯，许可证要合规**，规则见第 2 节。
4. **不存个人数据**：联系人、消息原文、金额、账号、验证码都不进知识库。证据截图和读屏摘录要先脱敏。
5. **一个 App 一个目录，按 bundle_id 命名**；跨 App 通用的知识放 `_shared/`。

---

## 2. 知识的四个来源

| 来源 | 什么时候用 | 产出状态 | 谁来做 |
|---|---|---|---|
| **A. 整合外部资料**（开源项目、论文、官方文档、社区整理） | 冷启动；新加一个 App 时先查一遍 | `lead` | 研究会话 |
| **B. 专门的 App 学习会话**（第 3 节） | 准备把一个 App 做进产品时 | `verified` | 学习会话，加上主人提供的测试账号和测试机 |
| **C. 运行时写回**（Agent 在任务中学到的东西） | 每次真实任务 | `observed` | Agent 自动写；人工定期审核 |
| **D. 回归失败和用户反馈** | App 更新之后，线上出错时 | 修正已有条目，或新增 `lead` | 回归任务、修复会话 |

### A. 外部资料的许可证判定

| 许可证 | 能怎么用 |
|---|---|
| 自有、MIT、Apache-2.0、BSD、CC-BY | **改写后吸收**：用我们自己的话重写，保留出处。MIT 等要求保留版权声明的，放进私有库的 `THIRD_PARTY_NOTICES.md` |
| 纯事实（官方 deep link 列表、App Store 元数据、社区整理的 scheme） | 事实本身可以记录；**一律标为 `lead`**，验证后再升级 |
| PolyForm、没有许可证、CC-NC、明确禁止竞品使用的 | **只作线索**：只记「谁报告了什么现象」，不复制文字、结构或格式，状态永远是 `lead`，直到我们自己验证后用自己的话重写。私有库的 `tools/check.py` 会强制检查这一条 |

**首次整合的结果**（2026-10-19，私有库 `deb7bc2`）：
- `catalog/apps.json`：72 个 App 的身份，合并了 LoopCtrl 的 `AppBundles.plist` 和 zhongerxin（MIT）核验过的 36 个 App。
- 37 个条目，覆盖微信、小红书、微博、淘宝、京东、健康、设置，以及跨 App 通用条目。来源有四类：LoopCtrl 源码注释里的实测、iCTRL 删除前的 App 提示、zhongerxin（MIT）的微信和微博读取深度及 10 个国内 App 的耗时表、leeguooooo/iphone-use-flows（MIT）的健康导出流程。
- leeguooooo/iphone-use 主项目（PolyForm）只取了 1 条线索（小红书的返回按钮）。
- **目前全部是 lead 或 observed，还没有 verified。**

### C. 运行时写回（和 SKILL.md 衔接）

新版 SKILL.md 让 Agent 把学到的东西追加到客户端的 `~/.loopctrl/notes/<bundle_id>.md`，比如功能在哪、出现过什么弹窗、标签和显示文字不一致、哪一屏慢、广告的 × 在哪。收集流程：

1. 定期把各台客户端的 `notes/*.md` 收进私有库的 `inbox/<日期>/`。**提交前先脱敏。**
2. 审核时，每一条笔记有三种去向：
   - 改写成 knowledge 条目，状态是 `observed`；
   - 合并进已有条目的证据；
   - 丢弃（个人信息，或者只出现过一次、无法复现的偶发情况）。
3. 被三次以上独立运行证实的 `observed` 条目，排进学习会话做 `verified`。

## 3. App 学习会话（标准作业流程）

**目标**：用一次 1–2 小时的会话，把一个 App 从「只有线索」做到「骨架、入口、弹窗和 3–5 个高频流程都 verified」。

### 3.1 准备

- **设备**：测试机，或者主人明确同意使用的设备，并且没有其他会话正在用。
- **账号**：测试账号，不用主人的真实社交账号做有副作用的操作。
- **记录 App 版本**：`device_info` 加上 iTunes Lookup `https://itunes.apple.com/lookup?bundleId=<id>&country=cn`。
- 先读私有库里这个 App 已有的条目，把要验证的 `lead` 列成清单。
- 打开 run 级计时。目前只能取 `config.timing` 的前后差值；将来可以用开源侧的 run 计时，见第 6 节。

### 3.2 七步清单

| 步骤 | 做什么 | 产出 |
|---|---|---|
| ① 身份 | 用 `resolve_app` 加 `launch_app` 确认 bundle_id；记录 App 名称的各种叫法 | catalog 条目 |
| ② 骨架 | 每个底部 tab 的首屏各读一次 `page_source{visible_only:true}`；记录导航栏或 tab 的识别锚点，以及优先使用的 identifier | `screens` 锚点；读屏摘录（脱敏后）存入 `evidence/` |
| ③ 入口 | 搜索入口：按钮还是输入框，真正的输入框在哪；逐条探测已知的 deep link：落地页、参数有没有带进去、是否有系统确认框 | `deeplinks`，每条都标成 verified 或「失效」 |
| ④ 弹窗 | **冷启动 3 次**（`terminate_app` 再 `launch_app`），加上热启动 1 次。记录开屏广告（有没有「跳过」、倒计时多长、× 在哪）、更新提示、权限框、登录墙、青少年模式 | `popups`，每个都带识别方式和处理方法 |
| ⑤ 流程 | 3–5 个高频任务（例如搜索、打开详情、读列表、发给自己）。每个任务先自由跑一遍，再按 playbook 格式写成流程，然后**确定性回放 3 次** | `flows/*.yaml`，3 次都通过才算 verified |
| ⑥ 时间 | 用 `logs` 里的 `⏱` 行和 `config.timing`，记录每个关键步骤的 p50 和 p90，以及慢页面 | `timing` 条目 |
| ⑦ 陷阱 | 把会话里遇到的所有意外按「条件 + 现象 + 建议」记下来：同名元素、返回按钮无效、手势被误认、文字和标签不一致等 | `traps` 条目 |

### 3.3 收尾

- 运行 `tools/check.py`。
- 更新 `app.yaml` 的 `verified` 记录：设备、iOS 版本、App 版本、日期。
- 提交到私有库，提交信息写明 App 版本和会话范围。
- 列出这次没覆盖的内容，作为下一次会话的待办。

**建议的顺序**（按使用频率和现有线索数量）：

| 批次 | App |
|---|---|
| 第一批 | 微信、小红书、淘宝 |
| 第二批 | 京东、拼多多、美团、支付宝（只读） |
| 第三批 | 抖音、B 站、高德 |

## 4. 证据和脱敏

- 每条 `verified` 都要附至少一项证据：`page_source` 摘录（只保留结构和框架标签，内容替换成 `<内容>`），或者 `logs` 的计时行，或者截图（原图只放在 `evidence/raw/`，不提交，`.gitignore` 已经排除）。
- 脱敏清单：人名和昵称、消息正文、手机号、地址、金额、订单号、账号 ID、头像。
- 证据文件名格式：`<日期>_<App 版本>_<屏幕或流程 id>.txt`。

---

## 5. 版本维护

- **App 更新监控**：定期用 iTunes Lookup 查 catalog 里每个 App 的最新版本。版本号变了，就把这个 App 所有 `verified` 条目的有效范围截止到旧版本，并安排回归。
- **回归**：把 `verified` 的流程每晚在测试机上跑一遍。通过的升级为 `regression`；失败的降回 `observed`，并开修复任务。
- **退化预警**：线上运行时，如果第 1 级选择器的命中率下降，说明 App 可能改了文案或结构，在失败之前就安排复查。
- **语言和地区**：标签按语言分变体。中文版和英文版的条目分开记录，不要混用。

## 6. 开源侧需要补的工具（LoopCtrl 本体）

学习流程现在能跑，但效率受限于下面几项。它们都是通用能力，属于开源侧：

| 工具 | 作用 | 对应调研文档 |
|---|---|---|
| 轨迹导出 | 每步的方法、参数、ref 匹配信息、settle 结果、前后屏幕指纹，供第 3.2 节第 ⑤ 步自动生成流程草稿 | control-speed-accuracy.md #12 |
| run 级计时，加上 p50/p90 | 第 ⑥ 步不用再手算差值 | #9、快速改进 2 |
| 广告关闭按钮检测 | 第 ④ 步的弹窗清单可以直接用 runner 给出的 `close_candidates` | 已提议为单独任务 |
| 笔记收集脚本 | 把客户端的 `~/.loopctrl/notes` 收进私有库的 inbox | 本文 2.C |
