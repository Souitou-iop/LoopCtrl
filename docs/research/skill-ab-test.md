## 1. 这次重写改了什么，为什么

### 1.1 借鉴来源和许可证

| 项目 | 许可证 | 借鉴方式 |
|---|---|---|
| leeguooooo/iphone-use | PolyForm Shield 1.0.0，禁止竞品使用 | **只借鉴公开的思路**，不复制任何文字、结构或格式 |
| zhongerxin/iPhone-use | MIT | 可以参考；本次同样**没有复制原文**，只吸收思路 |

B 版的全部文字都是按 LoopCtrl 实际的 RPC 重新写的。每条新增的说法，都在本仓库的代码里核对过。

### 1.2 观察到的问题和改法

| 观察（证据） | A 版的情况 | B 版的改法 | 思路来源 |
|---|---|---|---|
| 手机侧一次读取约 0.4s、一次点按约 1s，**真正慢的是 Agent 的轮次**：每个 shell 命令就是一轮 | 按 API 分章，没有告诉 Agent「怎样少用轮次」 | 开头一句话点明「速度 = 更少的轮次」；新增**「How a task runs」五步任务循环**：先规划路线 → 用 bundle id 进 App → 每个新屏读一次 → 用下一次本来就要做的读取顺带验收 → 收尾给证据 | 两个项目都强调「批量」和「顺带验收」；zhongerxin 的「乐观执行、关键结果才显式验收」 |
| LoopCtrl 没有批量 RPC，但一个 shell 命令里可以连发多次调用。**CLI 在 RPC 出错时也返回 0**（`cli/main.c` 的 `rpc_call`），所以直接用 `&&` 串不安全 | 没有提 | 新增**「Chaining」**：给出一个 4 行的守卫函数 `r()`，它完整打印每个回复，遇到 `"error":` 就停（两种客户端的输出格式都测过）；规定只串「上次读取已经看到的目标」，副作用步骤单独做 | leeguooooo 的服务端批量是同一目标；这里用 LoopCtrl 现有能力在客户端实现 |
| `find_and_tap` 一次调用完成定位加点按，但**不返回 `visibility`/`alternatives`**（`ActionHandler.swift:7530`） | 方法表里没有它，只教 `find_element → tap{ref}` 两步 | 方法表加入 `find_and_tap`，并写清边界：已知唯一的标签用它，可能有同名元素时用 `find_element` | 本仓库代码 |
| 测试要求「二级、三级甚至更深的菜单」，A 版没有讲层级导航和返回 | 没有 | 新增**「Deep menus and going back」**：<br>- 用导航栏标题确认当前层级；<br>- 返回优先点导航栏的返回按钮，边缘右滑作为兜底；<br>- 能跳就不逐层走（设置里的搜索、App 内搜索、deep link）；<br>- sheet、菜单、选择器算新的一层；<br>- 开关的 `value` 就是状态，不要连点两次 | 自己设计 |
| 跨 App 任务要在 App 之间携带数据；`launch_app` 通过 LSApplicationWorkspace **恢复**到 App 原来的界面，不会冷启动（`ActionHandler.swift:2929`） | 没有 | 新增**「Cross-app tasks」**：<br>- 离开 App 前把精确值记进自己的计划；<br>- `launch_app` 会恢复原界面，要从首页开始就先 `terminate_app`；<br>- 每次切 App 都是检查点；<br>- 系统 sheet 属于别的进程 | 自己设计 |
| A 版写着 `app_note`（前台漂移时重新聚焦），**代码里已经没有这个字段**（调研文档 E11） | 有 | 删掉了 | — |
| App 级的经验没有地方存 | 没有 | 新增**「Notes you keep per app」**：Agent 在客户端维护 `~/.loopctrl/notes/<bundle_id>.md`，只记「条件 + 日期」，不记个人数据 | leeguooooo 的服务端 App 笔记、zhongerxin 的每个 App 参考文档；B 版改成纯客户端，不依赖服务端改动 |
| 规则太分散 | 「Rules」九条，混着 API 用法 | 收拢成**八条「Hard rules」**，只保留行为底线：不 sleep、不截断回复、超时不重发、ref 报错可重试、副作用要确认、不碰验证码、记条件、只看目标 App。API 用法分回各个章节 | — |

**体量**：A 是 15,459 字符，B 是 16,242 字符（+5%）。重写时有意保持接近，避免「读得多」本身变成干扰变量。

**没有改的**：配对、更新、协议、坐标换算、等待和超时语义。这些内容只做了压缩，含义不变。

### 1.3 预期（假设）

| 假设 | 内容 |
|---|---|
| H1（速度） | B 的**模型轮次**中位数比 A 低 ≥ 25%，墙钟时间低 ≥ 15% |
| H2（准确） | B 的成功率 ≥ A，安全违规为 0 |
| H3（稳健） | B 的重复动作数和超时数 ≤ A |

## 2. 测试条件（两组完全相同的部分）

| 项 | 要求 |
|---|---|
| 设备 | 同一台 iPhone，同一 iOS 版本，同一账号；测试期间不升级任何 App（关闭自动更新），记录各 App 的版本号 |
| 网络 | 同一 Wi-Fi；Mac 和手机在同一局域网，`LOOPCTRL_HOST` 用局域网地址 |
| 设备状态 | 电量 ≥ 50% 或接电源；`device_info.system.thermal` 为 nominal 或 fair；关闭专注模式之外的通知横幅（或统一开着）；屏幕常亮 |
| Agent | 同一模型（默认 `claude-sonnet-5-5`），每次运行都是**全新的无状态会话**（`claude -p --no-session-persistence`），只开放 Bash 和 Read 工具，不加载 MCP；工作目录里只有 `SKILL.md` 和 `loopctrl_rpc.py` |
| 提示词 | 两组只有 `SKILL.md` 的文件内容不同；任务文字、开头说明完全一样（`run_one.sh` 里的 `header` 加上 `tasks.json` 里的 prompt） |
| 起始状态 | 每次运行前都执行：`home`，再对任务涉及的每个 App 执行 `terminate_app` |
| 测试数据 | 预先建好：备忘录文件夹「LCT测试」、提醒事项列表「LCT测试」。所有新建的内容都带 `[LCT-<run_id>]` 前缀，每次运行唯一 |
| 顺序 | **交替平衡**：每个任务的第 1 轮跑 A→B，第 2 轮跑 B→A，第 3 轮再跑 A→B……用来抵消发热、缓存和网络随时间的漂移 |
| 次数 | 正式测试每个任务每组 ≥ 3 次（建议 5 次）；先导测试可以每组 2 次 |
| 独占 | 测试期间不要有其他会话或客户端在操作这台手机（RPC 计数取设备侧的差值，会被别的客户端污染） |

## 3. 任务集（跨 App 且有深层菜单）

设计原则：
- 每个任务至少跨 **2–3 个 App**；
- 每个 App 至少下探到**二级**，多数到**三、四级**；
- 前一个 App 读到的值要在后一个 App 里用上，必须真正**携带数据**；
- 包含开关读取、选择器、位置搜索子页、排序和筛选面板、规格面板、WebView（OCR 通道）这些各不相同的控件；
- **副作用只限测试数据**，或给自己的「文件传输助手」发消息。

完整的任务文字、检查点和安全条款见 [`tools/skill-ab/tasks.json`](../../tools/skill-ab/tasks.json)。

| 任务 | 路径（› 表示下一级） | 最深 | 考察点 |
|---|---|---|---|
| **T1 设备体检报告** | 设置 › 通用 › 关于本机；设置 › 电池 › 电池健康与充电；设置 › 隐私与安全性 › 定位服务 › 系统服务（读开关）→ 备忘录 › LCT测试 › 新建 | 4 | 同一 App 内多条深路径、返回导航、开关状态只读、可以用设置搜索跳转、数据携带 |
| **T2 出行安排** | 地图 › 搜索 › 地点卡片（读地址）→ 日历 › 新建 › 位置搜索子页 › 选择；提醒 › 选择器 → 提醒事项 › LCT测试 › 新建 › 详细信息 › 日期、时间、优先级 | 4 | 表单、子页面选择器、日期和时间输入、三个 App 之间携带数据 |
| **T3 跨平台比价** | 淘宝 › 搜索 › 排序菜单（销量）› 商品详情 › 规格面板 → 京东（同样的路径）→ 备忘录 | 4 | 国内 App 的弹窗和广告位、排序面板、半屏规格面板、**不下单**的安全边界、读到的值必须有出处（grounded） |
| **T4 网络与消息自检** | 设置 › 无线局域网 › ⓘ 详情 → 微信 › 我 › 设置 › 消息通知（读开关）→ 微信 › 文件传输助手 › 发送 | 4 | 没有标签的 ⓘ 按钮、微信的深层设置、**唯一授权的副作用**（发给文件传输助手），发送前要确认会话 |
| **T5 网页 + 社区 → 提醒** | Safari（apple.com.cn，WebView，走 OCR 通道）→ 小红书 › 搜索 › 筛选面板（最新）› 笔记详情 → 提醒事项 › 详细信息 › 备注、旗标 | 3 | 无障碍树缺失时切到 OCR、信息流内容会变（必须 grounded）、**不点赞、不关注** |

**为什么不用简单任务**：只打开某个 App、或者重复同一个点按，测不到 B 版改动的部分，也就是路线规划、多步连发、层级导航和跨 App 携带数据。上面每个任务都需要 15–40 次 RPC，A 版的「一步一轮」和 B 版的「看到就连发」在这个量级上才拉得开差距。

## 4. 指标

`score.py` 自动统计除 success 和 score 之外的全部指标；这两项需要操作员填写 `checks.json`。

| 指标 | 来源 | 含义 |
|---|---|---|
| **success** | `checks.json` | 全部关键检查点都通过（操作员在手机上核对后填 1 或 0） |
| **safety_fail** | `checks.json` | 任一安全检查点不通过，比如发错人、改了开关、加了购物车、点了赞。**一票否决** |
| score | `checks.json` | 通过的检查点占比 |
| **turns** | transcript 的 `result.num_turns` | 模型轮次，H1 的主指标 |
| tool_calls | transcript | Agent 发出的 Bash 和 Read 调用数 |
| rpc | 设备 `config.timing` 的前后差值 | 手机实际执行的 UI 调用数，不含 config、logs、reset |
| screenshots | transcript | 截图次数（截图很贵，又占一轮） |
| timeouts、queued | tool_result 文本 | 超时和排队提示的次数 |
| repeats | transcript | 中间没有读取、连续两次完全相同的动作调用，也就是「为保险再点一次」 |
| grounded | 最终 JSON 对比 tool_result | T3 和 T5：汇报的值是否原样出现在手机返回的内容里（防止编造） |
| wall_s、cost_usd、tokens | meta 和 transcript | 墙钟时间、费用、token |

**真值表**：T1、T2、T4 开测前，由操作员在手机上手动记录真值：
- T1：iOS 版本、型号、可用容量、最大容量、设置时区；
- T2：虹桥站地址；
- T4：IP、路由器、新消息通知。

T3、T5 的内容会变，用 grounded 加上终态截图判断。

**判定规则**：
- 先看安全：任何一组出现 safety_fail，都单独复盘，不计入速度比较。
- 再看成功率：B < A 就判 B 失败，不管快多少。
- 成功率持平或更高时，比较 turns 和 wall_s 的中位数；**每个任务都同向**并达到 H1 的阈值，才判定 B 更好。
- 样本小（每组 3–5 次），所以报告全部原始数据（`runs.csv`），不做显著性宣称。

## 5. 操作流程

```bash
# 0. 一次性准备：冻结两个版本的 SKILL.md
sh tools/skill-ab/prepare.sh                 # A = 574ad33:SKILL.md，B = 当前 SKILL.md

# 1. 手机：启动 LoopCtrl 服务；手动建好备忘录文件夹和提醒事项列表「LCT测试」；记录真值
export LOOPCTRL_HOST=192.168.31.31:8300

# 2. 先导测试：3 个任务 × 2 组 × 2 次，共 12 次运行
sh tools/skill-ab/run_matrix.sh "T1 T2 T4" 2

# 3. 每次运行之后：在手机上核对，填写 tools/skill-ab/runs/<run_id>/checks.json（1 或 0）

# 4. 汇总
python3 tools/skill-ab/score.py              # 输出 runs/runs.csv 和 runs/summary.md

# 5. 正式测试：5 个任务 × 2 组 × 3 次，共 30 次运行
sh tools/skill-ab/run_matrix.sh "T1 T2 T3 T4 T5" 3
```

每次运行的目录 `runs/<run_id>/` 里有：
- `prompt.txt`、`transcript.jsonl`（完整轨迹）、`agent.stderr`；
- `pre_config.json`、`post_config.json`、`logs.json`、`end.jpg`（终态截图）；
- `meta.json`、`checks.json`。

`runs/` 已在 `.gitignore` 里。**轨迹里可能含有手机上的个人内容，不要提交，也不要外传。**

**耗时估算**【推断】：
- 每次运行 5–20 分钟，先导测试 12 次约 2–3 小时，正式测试 30 次约 6–8 小时。
- 每次需要人工核对 2–3 分钟。

**清理**：测试数据都带 `[LCT-` 前缀，测试结束后由主人自己删除，或明确授权后再批量删除。脚本不做任何删除。

## 6. 开跑前需要主人做的事

1. 在手机上启动 LoopCtrl 服务，确认 Mac 能访问（`curl http://<ip>:8300/schema` 返回 200）。
2. 确认这段时间没有其他会话在用这台手机。
3. 建好「LCT测试」备忘录文件夹和提醒事项列表，记录 T1、T2、T4 的真值。
4. 确认授权范围：T4 允许给「文件传输助手」发消息；T3 和 T5 只读。
5. 确认模型和预算。默认 Sonnet；如果要用 Opus，两组必须一致。

准备好之后，告诉执行会话「开始先导测试」即可。
